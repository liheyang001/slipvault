# Handoff — 2026-08-01

Everything for credit-pack payments is built and configured. One thing blocks
the first real purchase: **Google Sign-In fails with DEVELOPER_ERROR on the
Play-distributed build.** Sign-in is not optional — the credit ledger is keyed
on the Google `sub`, so nothing can be bought until it works.

---

## Update — sign-in solved, purchase sync was the next wall

**Sign-in works.** It took three Android OAuth clients. Neither fingerprint
shown in a console matched what was actually installed; the real one was read
off the device:

```bash
adb shell pm path nz.co.vesta.app
adb pull <path> installed.apk
apksigner verify --print-certs installed.apk   # keytool cannot read v3 signatures
```

That gave `E0:E6:14:0C:...` (`CN=Android, O=Google Inc.`), which is now
registered alongside the Play app-signing and EAS upload fingerprints.

**Then two test purchases went through Google but never reached RevenueCat.**
Play Console shows both as `Processed` (`GPA.3392-1141-1070-33671`,
`GPA.3398-2692-2597-40748`, credits_30, NZD 1.19 each). RevenueCat shows zero
revenue and no purchase on any customer, so no webhook fired and the ledger
never moved — balance still 58.

Cause: RevenueCat is told about a purchase by the **SDK posting the token**,
not by Google pushing to it. If that post fails, the order exists at Google and
nowhere else, and nothing retries. Fixed in `1865284` by calling
`syncPurchases()` at launch (after identity linking) and on every Paywall open.
**The fix needs a new build to take effect** — the installed build 4 predates it.

Worth noting the Worker was never at fault: its logs during the purchase show
only the client's balance polling, every request `Ok`.

## Start here tomorrow

1. **Build** (~20 min) — nothing to decide, the fix is already committed:
   ```bash
   npx eas build --profile production --platform android --non-interactive --no-wait
   ```
2. **Upload** to Play Console → Testing → Internal testing → Create new release
   → **Start rollout** (easy to forget; upload alone does nothing).
3. **Update on the phone** via Play Store, force-stop, reopen.
4. **Expect the two stranded purchases to recover by themselves** — balance
   should go 58 → 118 without buying anything. That is `syncPurchases()`
   doing its job, and it also proves the webhook path end to end.
5. **Then buy once more** to watch a clean purchase land, with the Worker log
   open:
   ```bash
   cd worker && npx wrangler tail --format pretty
   ```
   The one thing still unverified is what `product_id` RevenueCat actually
   sends. If it isn't `credits_30`, the Worker logs `unknown product <value>`
   and credits nothing — a one-line fix to `CREDIT_PACKS`, and no money is
   ever mis-credited either way.

## Done today

**Worker — deployed and verified by curl**

- `/rc-webhook` route with its own credential, separate from the app surface
- Idempotent crediting keyed on RevenueCat's event id (same event delivered
  three times → credited once, balance unchanged)
- Refuses anonymous (`$RCAnonymousID:`) buyers rather than stranding the money
- Null-prototype product map, so a `product_id` of `constructor` can't slip past
- `valuate` now requires sign-in; scan rate limits (10/min, 100/hr); 4 MB image
  cap; upstream errors no longer leaked to clients
- Migrations applied to D1: `credit_log.event_id` + unique index, `signup_ips`

**Client**

- RevenueCat SDK wired; identity linked at startup *and* before every purchase
  (an already-signed-in user was never linked — would have taken money and
  delivered nothing)
- Paywall rebuilt as a credit store; prices pulled live from RevenueCat
- Balance polling waits for the full expected amount, so a failed baseline read
  can't report an uncredited purchase as success
- Four generations of dead quota code removed; manual entry is now free and
  unlimited
- Renamed to **Vesta**, package `nz.co.vesta.app`
- Fixed: warranty reminders got a display-format date after the NZ date change,
  so reminders past the 12th of a month silently vanished
- Settings now shows the real version and build number (three builds all
  reported `v1.0.0`, which wasted an hour of debugging today)

**External configuration**

- Play Console: app created, build 4 live on internal testing, three consumable
  products, License testing enabled
- Service account + Play Developer API + permissions (403s traced and fixed)
- RevenueCat: Play Store app connected, three products **Published**, offering
  `default` with three packages — verified through the API, not the dashboard

## Still to do after sign-in works

1. **First test purchase** with the License-testing account, watching the
   Cloudflare log live. This settles the one open unknown: whether RevenueCat
   sends `credits_30` or something like `credits_30:base` as `product_id`,
   since the products use Google's new purchase-option model. If it doesn't
   match, the Worker logs `unknown product <value>` and credits nothing — a
   two-minute fix to the map, and no money is mis-credited either way.
2. **Verify crediting survives the app dying** — kill it right after paying;
   credits should still arrive, proving the webhook (not the client) is the
   source of truth.
3. **Remove `credits_dev_topup`** — the last task. Deliberately kept until
   purchases work, since it is currently the only way to obtain credits.
4. **Rewrite the store listing and privacy policy.** Both still claim
   "Free forever", "unlimited scans", "no account", "data never leaves your
   device" — all four now false. The pricing claim next to an in-app product
   list is a standard Google rejection reason, and the privacy claim feeds the
   Data Safety form, where a mismatch is a policy violation.
